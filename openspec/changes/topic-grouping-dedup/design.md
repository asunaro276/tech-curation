# Design

## Context

`adopt-jev-selection` の適用後、収集パイプラインの Select ノードは各記事を Jev の `worth`（Noul）で判定し、トピックごとに上位 K 本を残す。記事どうしを比べる仕組みはない。重複除去は Merge&Filter での URL 一致・タイトル先頭80文字一致・ランキングページ除外だけである。

レポートは `tech-curation/YYYY-MM-DD/daily.md` に1記事1セクションで書かれ、実行の最初に ob sync pull で vault 全体を取り込んでいるため、過去のレポートは Lambda から読める。ただし `daily.md` は表示用の Markdown であり、機械的に読むための構造は持たない。

## Goals / Non-Goals

**Goals:**
- 同じ出来事を扱う記事（レベル C）を1グループにまとめ、日をまたいだ重複を除く。
- 続報は残し、前回のレポートとつなぐ。
- 「まとめ漏れ」をフィードバックとして集め、判定基準を改善できるようにする。

**Non-Goals:**
- 異なるトピック間でのグループ化。
- 一度決めたグループのまとめ直し（全体として最適なグループ分けは目指さない）。
- この変更以前のレポート（`items.json` がない日）との重複判定。
- 「まとめ過ぎ」を専用の欄で集めること（`comment` で書いてもらう）。

## Decisions

### D1. 貪欲法 + Choice によるグループ分け
トピックごとに、worth の降順に1本ずつ処理する。

```
groups = []                    # 今日のグループ
past   = 過去 recency_days 日の items.json から、同じトピックのグループ
for article in sorted(candidates, key=worth, reverse=True):
    if article.url in past_urls: drop; continue          # Jev を呼ばない
    if not groups and not past: groups.append([article]); continue
    answer = jev.system_one(
        state = {"article": {title, source, body[:800]},
                 "today":  [{id: "g0", title, summary_hint}, ...],
                 "past":   [{id: "p0", date, title, summary}, ...]},
        questions = {"group": Choice(
            instructions = <grouping_criteria>,
            criteria = {"new": ..., "g0": ..., "same:p0": ..., "follow:p0": ...})},
    )
    new      → groups.append([article])
    gN       → groups[N].append(article)
    same:pK  → drop（ログに残す）
    follow:pK→ groups.append([article], follow_of=pK)
```
- 1記事あたり1回の呼び出しで済み、選択式なので「A≈B, B≈C なのに A≠C」という矛盾が起きない。
- 処理順で結果が変わるため、worth の高い記事がグループの核になるようにする。
- 今日のグループの説明には、そのグループに最初に入った記事のタイトルと本文の冒頭 200 文字を使う。
- 選択肢の数は「1 + 今日のグループ数 + 過去グループ数 × 2」。トピックごとに過去7日 × 約4グループで、約60個以内に収まり、Choice の上限 255 を超えない。
- 代替案: 全ペアを比べてからまとめる（呼び出し n²/2 回、矛盾の解消が必要）、埋め込みによるクラスタリング（別の API が必要）。どちらも規模に対して重いため採らない。

### D2. トピック間は並列、トピック内は逐次
グループの状態が前の判定結果に依存するため、トピック内は逐次実行する。トピック間は独立なので並列にする（`MAX_WORKERS` と同じ並列数）。1呼び出し 70〜500ms × トピックあたり最大十数本で、実行時間の増加は数秒程度。

### D3. 一次情報の判定は worth と同じ呼び出しで行う
Select の Jev 呼び出しの質問に `is_primary: Noul` を追加する（出力は課金されないので追加費用はほぼない）。GitHub のリリース由来の記事はコード側で一次情報として扱う。日本語の判定は、タイトルと本文の冒頭に平仮名・片仮名が含まれるかで行う。

代表記事の並び順のキーは `(is_primary >= 0.5, is_japanese, worth)` の降順とする。

### D4. グループの単位で本数を数え、候補の枠を広げる
上限本数 K はグループ数に適用する。まとめた結果として本数が足りなくならないように、Merge&Filter のトピック別の枠を `max(現行の枠, K × 3)` に広げる。

### D5. グループ単位の要約
`summarize_format` の入力をグループにする。代表記事の本文 1500 文字と、関連記事の本文を各 500 文字（最大4本）を渡し、「代表記事を軸に、関連記事にしかない観点も含めて1本にまとめる」指示で要約する。コンテンツ種別の判定は代表記事で行う。review / revise もグループを単位に扱う（除外はグループごと、書き直しは統合要約に対して行う）。

### D6. 日ごとの記録は `items.json` に分けて保存する
`daily.md` を解析するのではなく、レポートの生成時に同じディレクトリへ構造化データを書く。

```json
{
  "date": "2026-10-06",
  "groups": [
    {
      "no": 3,
      "topic": "Go",
      "title": "Go 1.25 Release Notes",
      "summary": "…",
      "follow_of": {"date": "2026-10-01", "no": 2, "title": "Go 1.25 RC"},
      "articles": [
        {"title": "Go 1.25 Release Notes", "url": "…", "source": "rss", "primary": true},
        {"title": "Go 1.25 の新機能まとめ", "url": "…", "source": "zenn", "primary": false}
      ]
    }
  ]
}
```
- `no` はレポート全体での通し番号で、レポートの見出しにも表示する。`dup=3` はこの番号を指す。
- 過去の記録を読むのは収集時（重複判定）と改善時（`dup` の解決）の2か所。

### D7. フィードバック欄の拡張は後方互換にする
`<!-- fb: relevance=, dup=, comment= -->` とし、パーサーは `dup=` があってもなくても読めるようにする。既存のレポートのフィードバックが読めなくなることを防ぐ。

### D8. 続報の表示
```
### #3 Go 1.25 正式リリース
📎 続報: [[tech-curation/2026-10-01/daily|2026-10-01]] の「Go 1.25 RC」
```
Obsidian の内部リンクを使い、vault 内で前回のレポートに移動できるようにする。

## Risks / Trade-offs

- [「同じ話題」と「続報」の境界が判定ごとにぶれる] → `grouping_criteria` に具体例を入れておき、`dup` フィードバックと `comment` をもとに自己改善ループで調整する。判定結果（選んだラベルと確率）はログに残す。
- [処理順によってグループの核が変わり、境界にある記事の所属が変わる] → 規模が小さいため許容する。worth の降順で処理して、価値の高い記事を核にする。
- [「まとめ過ぎ」が起きると、別の話題の記事がレポートから見えにくくなる] → 関連記事のリンクは必ず全件表示するので記事自体は失われない。`comment` での指摘を自己改善ループの入力にする。
- [`items.json` が同期の競合などで欠けると、その日との重複判定ができない] → 欠けた日はスキップして処理を続ける。URL の重複は次回以降の実行で拾える。
- [グループ要約の入力が長くなり、要約の質が落ちる・費用が増える] → 関連記事は最大4本・各500文字に制限する。

## Migration Plan

1. `adopt-jev-selection` を適用・アーカイブしてから着手する（`article-selection` spec と Select ノードを前提にするため）。
2. デプロイした日から `items.json` が作られ始める。最初の実行では過去の記録がないため、日をまたぐ重複判定は翌日以降から効く。
3. ロールバックは以前のコンテナイメージの再デプロイで行う。`items.json` は旧コードでは読まれないので、残っていても害はない。フィードバックのパーサーは旧形式も読めるので、新形式のレポートに記入されたフィードバックも旧コードで（`dup` を除いて）処理できる。

## Open Questions

- 候補の枠の倍率（K × 3）、関連記事の本文の文字数（500）と本数（4）の初期値は、実際のグループの大きさを見て調整する。
- `grouping_criteria` の初期文面に入れる具体例（リリースノートと解説・まとめは同じ話題、RC と正式版は続報、など）の範囲。
